# Testing and evidence

Every number shown in the deck or the video must come from a file listed in the evidence ledger below.

## Unit tests (Vitest)
- Cart math, option validation (required, min/max, hours, sold out), price deltas
- Session expiry and the "active in the last 30 s" extension
- Idempotency: duplicate `commandId`, **including a retry after another command slipped in between**
- Touch and AI changing the cart at the same time (transactions)
- State machine: QR claim during `ordering` keeps state; no payment without `confirming`; `requestCheckout` + `confirmCheckout` in one turn or one `/api/chat` request is rejected; an AI confirm within 1.5 s is rejected; a confirm-card tap needs no utterance; `paying → confirming` on edit; undo refused in `paying`
- Per-actor permissions: a phone token cannot send the card action; `cardAction` is refused for learned kiosks
- `/api/chat` history with tool turns is rejected
- Tool argument validation: negative and huge quantities, long strings, options from another item

## Agent evaluation set
About 20 utterances in Korean and English (the screen languages), each with the expected cart, grouped by complexity type (since 14-final:4 also 10, colloquial requests, and 11, the AI-only languages; since 15-judge-fixes:0 also 12, recovery: an applied order, a read-back while a choice is open, a change the item has no option for, a request the kiosk cannot serve; since 15-judge-fixes:1 an order typed before the dine option, then a dine tap after which the runner sends the held message again as the phone does, and a place the ticket machine does not sell; since 10-17 paying in cash on a card-only kiosk (`r-ko-cash`, `r-en-cash`: the cart unchanged, [Call staff] open and, by `noCheckout`, no `requestCheckout` or `confirmCheckout`); reported apart as groups `colloquial`, `language` and `recovery`; every case fails when any reply is the generic "Sorry, could you say that again?"):
1. several items at once
2. same item twice with different options
3. missing required choice → asks
4. remove/add ingredients
5. edit an existing line
6. sold out / out of hours → alternatives
7. count limits (toppings, on the learned Doughhouse kiosk)
8. unknown item → refuses
9. ambiguous ("one burger") → choice buttons

Report pass rate per type and per kiosk. Each case names its `kioskId` (default `malo`); the airport rail ticket machine has its own cases for passengers, destinations, a transit card's top-up, sold out, travel facts not in the data (staff) and checkout; the learned Doughhouse kiosk has two cases that the AI sends the user to pay on the kiosk and never offers to pay (a stand-in bridge reports each replay as done). Cases are in `evals/agent-cases.json`; `npm run eval:agent` runs them against real Gemini through the text agent's backend (`auto` by default: `GEMINI_API_KEY` from `.env`, with Vertex AI through gcloud application default credentials as the fallback; `GEMINI_TEXT_BACKEND=api` or `vertex` pins one; the result counts the model calls each backend answered) and writes `evals/results/<KST time>.json` and `.md`.

## End to end
- `npm run test:e2e`: Playwright against the dev server with the in-memory store, no model calls. `npm run test:e2e:live` runs only the `@live` tests (`/demo` typed order to real Gemini, "Play it for me" for each of the 9 `/demo` scenarios in `e2e/demo-scenarios.spec.ts` (all 9 played through on 10-13, 8-scenarios:4; one run, no saved log), and `e2e/voice.live.spec.ts`: the hero order spoken to Gemini Live by a synthetic TTS voice through Chromium's fake microphone; needs `GEMINI_API_KEY` in `.env`). Its relay mode (12-phone-app:9, ADR-012) speaks both fixtures to a second app on port 3110 with `GEMINI_LIVE_BACKEND=vertex`, so the phone's voice goes through the `kibo-voice` relay to Vertex AI Live (gcloud application default credentials); the relay runs in the same process as that dev server (`scripts/e2e-relay-stack.ts`, which Playwright starts only for `test:e2e:live`) so both share the in-memory store, and every relay run goes to `evidence/voice-e2e-relay.json`. Both modes check that no instructions reach the browser (the `/api/live-token` reply and every WebSocket frame). The voice fixtures in `e2e/fixtures/` come from `npm run fixtures:voice` (Gemini TTS); no real person's voice.
- **Evidence files change only on purpose (R-021, I-099).** The specs that measure (`e2e/voice.live.spec.ts`, `e2e/learned.spec.ts`, `e2e/kiosk-touch.spec.ts`, `e2e/kiosk-touch-efficient.spec.ts`) write to `evidence/` only with `EVIDENCE=1` (`evidencePath` in `scripts/evidencePath.ts`); any other run writes the same data to `test-results/evidence/` (git-ignored), so `npm run test:e2e`, `npm run test:e2e:live` and a QA step never change a cited number. To record a voice measurement: `npm run evidence:live` (`EVIDENCE=1 npm run test:e2e:live`), then update `docs/plan/NUMBERS.md` in the same commit; `scripts/numbers.test.ts` fails while the two disagree.
- Two devices in two real browsers (`e2e/two-device.spec.ts`, 12-phone-app:5): a 1440×900 laptop on `/kiosk` with the pairing panel and a separate 390×844 phone Chromium that opens `/app`, taps [Scan a kiosk] and reads the kiosk QR with a fake camera, then orders to the order number through the real API and session streams (the AI's tool calls sent with the phone's device token). Its `@live` test plays `hero-ko.wav` through the phone's fake microphone to Gemini Live and waits for the hero lines on the laptop kiosk.
- Real phones (iOS Safari, Android Chrome) from QR scan to order number; three consecutive passes the day before recording.
- iOS checks: mic permission persistence across visits, silent switch, volume, AI voice feeding back into the mic, KakaoTalk/Naver in-app browsers. Start with `/mic-test` (not linked, noindex): browser and in-app detection, the mic through the voice worklet with a level meter and sample rates, a 24 kHz tone through the AI voice's playback path, a reload check, and a one-line result to paste in the team chat. It sends nothing to the server and keeps no audio (`e2e/mic-test.spec.ts` checks both with Chromium's fake microphone).
- Live reconnect (network switch, screen lock).

## Measurements
- **Touch vs voice:** the same final cart, 3 touch runs and 3 voice runs; report medians of taps/utterances and seconds. Protocol and JSON template: `scripts/measure-touch.md`, `evidence/human-runs.template.json`. The `/demo` end card (D3, MALO) shows this session's own counts next to the touch numbers: the medians from `evidence/human-runs.json` when it exists, else the automated efficient run's taps only (`src/lib/demo/evidence.ts`, bundled at build time).
- **Latency:** (a) end of speech → first audio reply ≤ 2 s; (b) end of speech → kiosk highlight ≤ 3 s. The deck uses the median of (b).
- **Real kiosks:** screens, taps and time for the hero order at two real fast-food kiosks (notes only, no photos). The simulator's tap count should be within ±20%.
- **Cost per session:** Gemini tokens for one hero order by text (`/api/chat` path) and by voice (one Live session), `npm run measure:cost` (`scripts/measure-cost.ts`): 4 user turns (the order, both fries large, no dessert, "I'll pay"), 3 runs each, token counts only. The official Gemini API prices (with their URL and read date) are stored in the evidence file's `prices`, and `scripts/cost.ts` turns the tokens into USD per order (`costUsdPerOrder`, checked by `scripts/cost.test.ts`); re-read the pricing page before quoting it.
