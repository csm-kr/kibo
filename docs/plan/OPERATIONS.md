# Operations during judging and the finale

Not injected into harness steps (lives under `docs/plan/`).

## Deploy
Run `sh scripts/deploy.sh` (needs `gcloud` logged in to `kibo-2026`). It runs `npm run build` locally first and stops if it fails, notes the revision `/api/health` reports, runs `gcloud run deploy kibo --source .` (Cloud Build builds the `Dockerfile`; `.gcloudignore` and `.dockerignore` keep `.env*`, docs, tests and videos out of the upload but keep `evidence/`, `data/`, `skills/` and `package.json`, which `src/` imports; `scripts/build-context.test.ts` checks this), then waits up to a minute for `/api/health` to report a **new** revision. Its last line is `DEPLOYED <revision>` or `DEPLOY FAILED: <reason>`. A failed Cloud Build leaves the old revision serving, so `/api/health` alone answering is not proof of a deploy (10-13); read the last line. `scripts/deploy.test.ts` runs the script with fake `gcloud`, `curl` and `npm`.

| Flag | Why |
|---|---|
| `--project kibo-2026 --region asia-northeast3` | Region is mandatory: the local gcloud default points elsewhere, and Firestore is in `asia-northeast3` |
| `--service-account kibo-runtime@…` | Runtime account with only `datastore.user`, access to `gemini-api-key` and `aiplatform.user` (the text agent's Vertex AI fallback) |
| `--allow-unauthenticated` | Judges and phones open the app without a Google login; the API's actor tokens and limits protect it |
| `--min-instances 1 --max-instances 3` | No cold start during judging; cost ceiling (the per-IP limit is per instance, so at most 3×) |
| `--concurrency 80` | Each open screen holds one SSE request (ADR-010) |
| `--timeout 900` | Above the events route's own 15 min cap, so the server, not Cloud Run, ends each SSE stream cleanly; `EventSource` reconnects on screens in use. Was 3600 until 12-phone-app:7 (see "Open streams and cost") |
| `--cpu 1 --memory 1Gi` | Enough for the Next.js server and the Firestore listeners |
| `--set-secrets GEMINI_API_KEY=gemini-api-key:latest` | The key comes from Secret Manager, never from a file or flag value; voice and the text agent use it |
| `--set-env-vars STORE=firestore,…` | Firestore store (the app refuses `STORE=memory` in production unless `ALLOW_MEMORY_STORE=1`), project, text backend `auto` (the key first, Vertex AI on 402, 429 or 5xx/network errors; I-104, I-105), model ids (ADR-011), text thinking `low`, and `PUBLIC_ORIGIN` = `https://kibo-<project number>.asia-northeast3.run.app` (the script reads the number with `gcloud projects describe`), so every QR link and the kiosk's "<host>/app" line use the deterministic service URL. With `SHORT_APP_URL` set in the deploying shell (e.g. `SHORT_APP_URL=kibo-2026.web.app sh scripts/deploy.sh`), it is added too, and the kiosk shows that host instead of "<host>/app"; QR links do not change. `--set-env-vars` replaces every variable, so a deploy without it removes it from the service |

**Short address (`kibo-2026.web.app`, 12-phone-app:6):** the kiosk's pairing line is a host people type on a phone, and the Cloud Run host is 45 characters (I-167). Firebase Hosting on `kibo-2026` serves only redirects, no files and no Firebase SDK in the app: `firebase.json` (public folder `hosting-public/`, empty) sends `/` to `<Cloud Run>/app` and every other path to the same path on Cloud Run (302; the first match wins; a `/:path**` glob did not match paths like `/app/scan`, so the second rule is a named-group regex). Live since 10-13 about 16:50 KST, deployed by the orchestrating session through the Hosting REST API; redeploy from `firebase.json` after a change (a person or the orchestrator, never a harness step). Then deploy the app with `SHORT_APP_URL=kibo-2026.web.app`; the app ignores a value that is not a bare lowercase host (one log line), and `scripts/deploy.sh` refuses one with characters other than `a-z0-9.-`. Check: K1 and the landscape pairing panel show `kibo-2026.web.app` on one line, and `https://kibo-2026.web.app` opens `/app`.

**Open streams and cost (12-phone-app:7):** a cost check of the GCP project on 10-13 (orchestrating session, billing console, no saved file) found Cloud Run billed as "active" almost all the time: each SSE stream stayed open up to the 3,600 s request timeout and `EventSource` reconnected at once, so one forgotten `/kiosk` or `/demo` tab kept an instance busy. Active time cost about KRW 4,350 per instance per day against about KRW 820 for an idle minimum instance, about KRW 110,000 until judging ends on 11-06 if nothing changed (own estimate from those rates). Now: (1) a hidden tab closes its stream after 60 s and reopens it when visible; (2) a phone or `/demo` screen with no session change and no pointer or key input for 20 min closes its stream and shows "Paused · Tap to continue" until tapped; **kiosk tabs (`/kiosk`, `/learned/*`, `/demo` "Use my phone instead") never pause while visible, by design** (12-phone-app:10, I-172: a kiosk waits on K1 with its QR, and a learned kiosk's bridge must replay as soon as a phone orders), so a visible kiosk tab keeps an instance active: **close kiosk tabs after a demo**; (3) the events route ends every stream after 15 min with a final comment, and `EventSource` reconnects on screens still in use; (4) `--timeout 900`, above that cap. Pings (one short request every 30 s per screen) are unchanged. After the next deploy, check in the Cloud Run metrics that billable instance time falls to the minimum instance when no one has a screen open (unverified until then).

**CI (`cloudbuild.yaml`, 15-judge-fixes:5; not wired yet):** a Cloud Build trigger on push to `main` runs, in order: `npm ci` and `sh scripts/ci-check.sh` (lint, unit tests, production build, `npm run check:attacks` against that build with the memory store, never a deployed URL, no AI), builds and pushes the image to `asia-northeast3-docker.pkg.dev/kibo-2026/cloud-run-source-deploy/kibo:<build id>`, deploys it with the same flags as `scripts/deploy.sh` but `--no-traffic --tag candidate`, polls `/api/health?deep=1` on the candidate's own tag URL for up to 2 min (200, and `/api/health` names that revision), and only then sends 100% of traffic to that revision (`update-traffic --to-revisions <rev>=100`: the same as `--to-latest` unless another build made a newer revision meanwhile). Any failed step leaves the serving revision untouched. `PUBLIC_ORIGIN` comes from Cloud Build's `$PROJECT_NUMBER`; `SHORT_APP_URL` and `VOICE_RELAY_URL` are trigger substitutions `_SHORT_APP_URL`, `_VOICE_RELAY_URL` (empty leaves them off, as in `deploy.sh`). Run the same checks locally with `sh scripts/ci-check.sh` (last line `CI PASSED` or `CI FAILED: <step>`; it rewrites `evidence/forged-commands.json`, I-099). `scripts/ops.test.ts` checks the script's order and the YAML's step order and flags. **A person creates the trigger** (connect the GitHub repo, branch `^main$`, config `cloudbuild.yaml`) and gives the Cloud Build service account `roles/run.admin`, `roles/artifactregistry.writer` and `roles/iam.serviceAccountUser` on `kibo-runtime`. The trigger clones the repo, so `.gcloudignore` (which drops `scripts/`) does not apply; a manual `gcloud builds submit --config cloudbuild.yaml` would upload without `scripts/` and fail at the checks. Unverified until the first triggered build: that `node:24` builds the Next.js app as the Dockerfile does, and that a tagged revision with `--min-instances 1` keeps its idle instance billed (the `candidate` tag moves to each new revision, so only one revision holds it). During the judging freeze, disable the trigger. `scripts/deploy.sh` stays the manual path.

**Setup once (`scripts/ops-setup.sh`, 15-judge-fixes:5; applied 10-15 by the orchestrator: Firestore TTL ACTIVE on all three collections; the uptime check `kibo-deep-health-dndeoHIaU58` and the policy "KIBO /api/health?deep=1 failing" (owner e-mail) already existed from a manual setup, and the run added a second channel and an empty policy "KIBO deep health failing", both harmless; delete them in the console if wanted, I-280):** prints by default, `sh scripts/ops-setup.sh --apply` runs it; safe to run again (each resource is looked up before it is created). It enables the Firestore TTL on `expiresAt` for `sessions`, `sessionSecrets` and `pairCodes`, creates the uptime check `kibo-deep-health` (HTTPS `/api/health?deep=1`, every 5 min, 3 regions, 200 expected), e-mail channels for `ALERT_EMAILS` (comma-separated, set in the shell; never written in the repo) and the alert policy "KIBO deep health failing" (the check reports failure for 10 min). Tested with a fake `gcloud` in `scripts/ops.test.ts`; the real gcloud flags were not run (unverified).

**Firestore TTL (once, by a person):** TTL policies delete expired documents on `expiresAt`: `sessions`, `sessionSecrets` and, since 12-phone-app:3, `pairCodes` (the kiosk's 6-digit pairing codes). Enable the new one with `gcloud firestore fields ttls update expiresAt --collection-group=pairCodes --enable-ttl --project kibo-2026` and check it with `gcloud firestore fields ttls list --project kibo-2026`. Without it, used-up codes stay in the collection (they no longer work, because a code must also be the session's current `sessionSecrets.pairCode`), and the 1,000,000 codes slowly fill up. TTL deletes up to about a day late, which the code reservation allows for.

**Which backend serves what:** voice uses the Gemini API key (ephemeral tokens exist only there) while the key can pay, and the `kibo-voice` relay on Vertex AI Live when it cannot (ADR-012, `GEMINI_LIVE_BACKEND=auto`, needs `VOICE_RELAY_URL`). The text agent uses the key while it works and falls back to Vertex AI, billed to the GCP account, per call; after 3 billing errors (402) within 5 minutes an instance skips the key for 10 minutes. Without `GEMINI_API_KEY`, or with its prepaid credits used up (HTTP 402, logged as `gemini billing error (402)` or `voice key probe: Error 402` for voice and `gemini text fallback api->vertex (402)` for text), voice goes through the relay (without a relay it fails and the phone falls back to text); the text agent on Vertex AI and touch ordering still work. Top up the credits in AI Studio (a person's task) to bring voice back to the faster direct path; an instance re-probes the key 10 min after it saw it fail. `GEMINI_TEXT_BACKEND` and `GEMINI_LIVE_BACKEND` = `api` or `vertex` pin one backend.

**Deploy order with the relay (12-phone-app:9):** (1) `sh scripts/deploy-voice.sh`, read the `kibo-voice` URL it prints; (2) `VOICE_RELAY_URL=wss://<kibo-voice host>/ws sh scripts/deploy.sh` (with `SHORT_APP_URL` as usual; the script refuses anything but `wss://<host>/ws`); (3) `curl <service URL>/api/health?deep=1` shows `liveRelay: "ok"`. `--set-env-vars` replaces every variable, so a later `deploy.sh` without `VOICE_RELAY_URL` turns the fallback off. Rolling back `kibo-voice` alone is safe: with the relay down, `auto` still uses the key while it works.

**Voice relay `kibo-voice` (12-phone-app:8; first deployed 10-13 by the orchestrator, revision `kibo-voice-00001-6kz`, current `kibo-voice-00005-ptd` since 10-17, `https://kibo-voice-407514467119.asia-northeast3.run.app`):** a second Cloud Run service from this repo (`voice-relay/`, `Dockerfile.voice`), so voice can run on Vertex AI Live (post-paid, `us-central1`, the only region that served `gemini-3.8-live` on 10-13) instead of the key's prepaid credits; the phone uses it since 12-phone-app:9 when `/api/live-token` says so. Deploy with `sh scripts/deploy-voice.sh` (a person or the orchestrator): it bundles locally (`npm run voice:build`), builds `Dockerfile.voice` with Cloud Build (`voice-relay/cloudbuild.yaml`, image in the `cloud-run-source-deploy` repository of `asia-northeast3`, assumed to exist from the kibo source deploys, unverified), deploys `kibo-voice` in `asia-northeast3` with the same runtime service account (its `aiplatform.user` covers Vertex Live), `--min-instances 0 --max-instances 2 --timeout 900 --session-affinity`, no secret, and ends with `DEPLOYED <revision>` / `DEPLOY FAILED: <reason>` after `/health` reports a new revision (`scripts/deploy-voice.test.ts`). The browser's first WebSocket message carries the device token; the relay runs the token route's checks and budgets. `npm run voice:relay-check` drives one real text turn through a local relay. The health path was `/healthz` until 12-phone-app:10; Cloud Run answered it with Google's own 404, so the first deploy printed `DEPLOY FAILED: /healthz did not answer` although the WebSocket worked (I-174). Redeploy once so the service answers `/health`.

**Never end a Cloud Run URL path in `z`.** Cloud Run reserves such paths (its "reserved URL paths", e.g. `/healthz`, `/readyz`) and answers them itself, so the app never sees the request. Health paths here are `/api/health` and `/health`.

**Roll back:** list revisions with `gcloud run revisions list --service kibo --region asia-northeast3`, then `gcloud run services update-traffic kibo --to-revisions <rev>=100 --region asia-northeast3`. A later deploy sends traffic to the new revision again.

**Uptime check:** in Cloud Monitoring, an HTTPS uptime check on `<service URL>/api/health?deep=1` every 5 min from at least 3 regions, alerting both team members by email. The deep check reads the store (a session id that never exists must come back empty), asks the Gemini API for the text and live model ids, makes one 1-output-token generation through the text backend (`textGenerate`, the key with the Vertex AI fallback) and one on the API key (`keyGenerate`, the key voice uses), and creates and discards a one-use ephemeral token (`liveToken`), and with `VOICE_RELAY_URL` set asks the relay's `/health` (`liveRelay`, else `off`); 200 when all pass, 503 otherwise, body `{ ok, checks: { store, textModel, liveModel, textGenerate, keyGenerate, liveToken, liveRelay } }`. While `liveRelay` is `ok`, a failing `keyGenerate` alone keeps 200 (voice still works through the relay); read `keyGenerate` in the body to see whether the credits need a top-up. Only the two generations cost anything: two tiny requests per uptime check (every 5 min), negligible. Model lookups and token creation are free and kept passing on 10-13 while the key's credits were used up, which is why the generations were added (I-104). Results are cached for 60 s per instance, so the check makes at most six upstream calls a minute. Plain `/api/health` is the cheap liveness probe.

## Two-device demo
A laptop stands in for the kiosk and a real phone orders (USER_JOURNEY J1, J2). Checked end to end by `e2e/two-device.spec.ts` (two browsers through the real API; the `@live` test speaks `hero-ko.wav` to Gemini Live).
1. **Laptop:** open `<service URL>/kiosk?k=malo` in Chrome, full screen (F11 or ⌃⌘F), landscape. KIBO's pairing panel beside the kiosk shows a large QR, `<host>/app` and a 6-digit code, and "Waiting for a phone".
2. **Phone:** scan the QR with the camera app and tap the link; or open `<host>/app` (installable from the browser menu) and tap [Scan a kiosk], or type the 6-digit code and tap [Connect].
3. **Allow** the camera (only for [Scan a kiosk]) and the microphone when the phone asks. The panel now says "Phone connected at <time>".
4. **Talk:** [Start], [Turn on the microphone], [Eat here], then say the order. The kiosk lights up the lines; say "I'll pay", tap [Yes, pay now] on the phone, then on the laptop tap 카드 and 카드 넣기. The order number shows on both.
5. **KakaoTalk, NAVER and other in-app browsers** often block the microphone and camera. The phone shows a note: open the link in Safari or Chrome (the in-app menu's "open in browser"), or copy it on the microphone screen before connecting. [Order here by typing] still works in the app.
6. **Stuck or a lost phone:** [다른 휴대폰 연결] on the kiosk issues a new QR and code and releases the old phone. Voice needs the Gemini API key's credits (`keyGenerate` ok in `/api/health?deep=1`) or the relay (`liveRelay` ok); without either the phone falls back to typing.

Re-read the limits before judging starts; the higher tier buckets apply only if the project is upgraded.

**Spend caps and the shared billing account (read 10-18, I-403).** The Gemini API key's billing account also pays for four other projects, and its tier's monthly spend cap and prepaid credits are account-wide (Tier 1: $250 a month; Tier 2 after $100 paid and 3 days: $2,000; https://ai.google.dev/gemini-api/docs/rate-limits). Credits used up answer 402; a reached cap or daily quota answers 429 until it resets. Both now send voice to the Vertex relay and text to Vertex (post-paid, slower). The deep health check alone makes about 1,770 `generateContent` calls a day (about 18% of Flash's 10,000 a day). Before judging the owner checks by hand: the AI Studio credit balance and auto-reload (aistudio.google.com/billing), the tier (aistudio.google.com/projects) and October's spend against its cap (aistudio.google.com/spend). If the key fails anyway: `gcloud run services update kibo --update-env-vars GEMINI_LIVE_BACKEND=vertex,GEMINI_TEXT_BACKEND=vertex --region asia-northeast3 --project kibo-2026` (`--update-env-vars`, never `--set-env-vars`, which drops the other variables).
