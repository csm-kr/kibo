# KIBO Learn changes

Changes to `learner.mjs`, `driver.mjs`, `runner.mjs` and `audit.mjs` after the end of phase 12, so blind-kiosk baselines and finals can say exactly which learner they ran (`spikes/blind-kiosks/PROTOCOL.md`).

## 10-13, 13-blind-kiosks:2: crash fix (I-185), part of the baseline
- **Nudge before the function responses.** After 60 turns without `testSkill`, every 20th turn adds "Stop exploring. Call records(), write the skill JSON from it, and call testSkill now." to the user turn that holds the function responses. It was appended after them, and Vertex AI refuses a user turn whose text part follows its function responses with HTTP 400 "Requests ending with a model turn are not supported." (checked 10-13 with one-off requests to `gemini-3.8-flash`: text after the responses 400; text before, a separate user turn, or the text inside a function response 200). It now comes first in the same turn; the words and the rule for when it fires are unchanged.
- **One retry on 429, 500 and 503** after 5 s; a 400 is not retried. A non-JSON error body no longer crashes the process; the loop ends with the status logged, as for any other API error.
- Test: `node --test spikes/kibo-learn/learner.test.mjs` runs the real learner loop against a fake Vertex (`fake_vertex.mjs`, a `--import` preload) and a fake `gcloud`, with no network; it needs Chrome, like `test_audit.mjs`.
- Exploration is unchanged: prompts, tools, the finish gate, the audit and the limits are the same as at the end of phase 12. The OpenAI loop (development only) is untouched.

## 10-13, 13-blind-kiosks:3: the process always exits (I-187), part of the baseline
- A bk2 run in step 1 wrote `learn-stats.json` and then never exited. Reproduced: an `audit` whose start recipe fails leaves the browser that `freshMenu` in `audit.mjs` opened (it is outside the `try`), and that connection keeps Node alive after the learner's last line.
- The loop now runs inside `try`; on any way out (finish, turn cap, token cap, API error, a thrown error) the main browser is closed, `learn-stats.json` is written (with `error` after a crash) and the process exits with `process.exit` (0, or 1 after a crash), which also ends any browser the audit left open. `audit.mjs` itself is unchanged.
- Tests in `learner.test.mjs`: a failed-start audit (hung for the 60 s test limit before the fix, 5 s after), a dropped connection, the token cap. The bk3 and bk4 baselines ran with this learner; bk1 and bk2 (step 2) ran without it, which changes nothing about how they explored.

## 10-13, 13-blind-kiosks:4: learner gaps (the learner for the final runs)
Fixes for the failure patterns in `spikes/blind-kiosks/results/BASELINE.md`, made and tested only on the dev set (Doughhouse, Gureum Darak Coffee) and on synthetic fixtures written from the pattern descriptions (`fixtures/patterns/stepper.html`, `wizard.html`). The four test kiosks were not opened. Numbers in brackets are the BASELINE pattern numbers.

**New skill format** (backward compatible: every older skill still runs):
- A step may carry `"within": "<text>"`: among the targets that match, the one whose closest ancestor holds that text (the `+` in the shot's own row, the `수량 더하기` on the item's own cart line) [1, 5].
- Recipe op `chooseOptions`: per option group of the line's item, in catalog order, the group's own `select` steps (or the op's steps) once per chosen option, then the group's `after` steps (a wizard's `다음`) [1, 6].
- Option groups may have `"type": "quantity"` with `maxQty` per option (an order repeats the name once per count), `select`, `after`, and `"appliesWhen": "<group>=<option>"` [1, 6, 9]. `forbiddenLabels` lists the kiosk's checkout and payment buttons [3].
- One pure planner, `plan.mjs` (placeholders, `forEach`, `repeat`, `chooseOptions`), is used by the runner, the lint and the blind-kiosk grader, so "what would be clicked" is computed the same way everywhere. The product bridge (`src/lib/bridge/recipe.ts`, `src/lib/adapters/learned.ts`) replays `within`, `chooseOptions`, `select` and `after` with the same rules, with unit tests; `skills/doughhouse.json` is unchanged and still valid.

**Driver and runner** (`driver.mjs`, `runner.mjs`):
- Never taps a payment or checkout control: `act` refuses a step or target whose label or text holds 결제, 카드, 간편결제, 쿠폰, 상품권, 주문하기, pay, card or checkout (the grader's list) or a `forbiddenLabels` entry; the runner refuses a whole order before opening the kiosk when its plan names one [3].
- Elements with a control role (`button`, `radio`, `checkbox`, `tab`, `option`, `switch`, `menuitem`, `link`) are tappable labels even without a pointer cursor or `onclick` [8]. Same rule in `src/lib/bridge/labels.ts`.
- A label that matches several elements fails before any click with the text near each and "add within"; a missing label names the labels that contain it [1, 5, 8]. The snapshot adds `REPEATED LABELS: "+" ×2 near [에스프레소 샷 | 바닐라 시럽]` [1, 5].
- `clickIfVisible` on an ambiguous label now fails, as the product bridge already did, instead of clicking the first match.
- Cost: a replay is slower. The Doughhouse holdout took 0.9–1.7 s per order with this runner against 0.55–0.7 s before (same skills, `results/dev/gemini-doughhouse-*/holdout.log` vs `results/run3/holdout.log`), because every step marks the labels again and reads the target's text for the forbidden check (I-191).

**Learner** (`learner.mjs`, `lint.mjs`, `audit.mjs`):
- `act` takes `"steps"` (several steps, one screen back); `record` takes a JSON array [2].
- The finish gate counts different passing orders of the exact same skill over several `testSkill` calls (still ≥ 3, none failed); any change to the skill starts again. `testSkill` says where the gate stands [4].
- `lintSkill` (run by `testSkill` and `finish`) rejects options named like navigation or stepper buttons (다음, 확인, 담기, `+`, "… 더하기"), a quantity group without `select` or `maxQty`, an `appliesWhen` that names no option of another group, and recipes that click a payment control [1, 3, 6, 9].
- The audit treats payment and checkout labels as known and never probes them [3]. It also opens every item that is not sold out and lists in `missingOptions` the choices on its first screen (radios, checkboxes, "+n원" labels) that none of its groups name; informational for `audit.ok`, but `finish` refuses once per skill while it is not empty (a second `finish` of the same skill is accepted, so a false alarm cannot block a run). Added after the first OpenAI dev run below left out a whole topping group.
- The prompt asks for `audit` as soon as the catalog has every category, before testing [7], and describes the new fields. "A non-pizza item" became "an item from another category". After 60% of the token budget without a passing gate, a nudge every 10th turn says to write the skill [2, 7].
- I-188: the gcloud access token is fetched again before it is 50 min old (`TOKEN_MAX_AGE_MS`) and once after a 401, then the request is retried.
- I-187: `audit.mjs` `freshMenu` closes its browser when the start recipe fails.
- Opt-in trace (`TRACE_DIR`): after every turn `turn-<n>.json` (tools, labels and ids only, one-line result, discoveries so far, tokens) and `turn-<n>.jpg` (the kiosk viewport, 720 px wide, JPEG quality 70), and `trace.json` (kiosk id, model, start and end, gate). It changes no request (tested).

**Token cost** [2]:
- Old screen trees, failed-test snapshots and old `records()` lists are replaced in blocks, every 4 turns keeping the last 2, instead of rewriting one older turn on every turn; between prunes a request only grows at its end, so the implicit prompt cache can serve the rest. Between 2 and 5 recent screens stay (before: 4).
- `compactTree` drops unnamed and emoji-only images, separators and link urls, and folds runs of identical lines into one "(×n)"; the TAPPABLE LABELS line is untouched (tested on a fixture screen).
- `learn-stats.json` records `cachedInputTokens` from `usageMetadata.cachedContentTokenCount` on the Gemini path too.
- Measured on Doughhouse with Gemini (`gemini-3.8-flash`, cap 1M, one run each, 10-13): the learner before this step, with only the cached-token count added, finished in 59 turns, 9.2 min, 416,373 input tokens of which 191,500 cached (46%), 12,319 output (`results/dev/gemini-doughhouse-before/`); this step's learner (all changes above except the `missingOptions` audit, which came later) finished in 38 turns, 4.0 min, 352,822 input tokens of which 196,701 cached (56%), 20,279 output (`results/dev/gemini-doughhouse-after/`, with a trace). Uncached input fell from 224,873 to 156,121 tokens (−31%). The after run also has fewer turns (several steps per `act`), so the cache and the turn count are not separated. Both skills replay the Doughhouse holdout 4/4 and catch the rule violation. Cost in money is left out: the Vertex AI pricing page could not be read on 10-13, and the Gemini API prices in `docs/TESTING.md` are not Vertex prices (R-001).
- Not changed: what the learner explores or decides is driven by the prompt and tools above, not by the pruning; the input-token cap still counts every prompt token, cached or not, as in the baseline.

**Tests** (no AI, need Chrome): `node --test spikes/kibo-learn/patterns.test.mjs` (17), `node --test spikes/kibo-learn/learner.test.mjs` (12), `node --test spikes/blind-kiosks/grade/test/` (24), `node spikes/kibo-learn/test_audit.mjs <pizzaUrl> <blindUrl>` (4/4).

**Dev-set runs with OpenAI** (development only, never published; `results/dev/`): see `results/dev/README.md`.

## 13-blind-kiosks:7 — the payment-label rule matches whole labels (I-193)
Informed by a test kiosk: the bk2-bakery final run (`spikes/blind-kiosks/results/bk2-bakery/final/notes.md`) had 5 unsafe orders because the driver refused its timeout modal's only button, `계속 주문하기` (continue ordering), for containing `주문하기`. Built and tested on a synthetic fixture only (`fixtures/patterns/modal.html`, `modal.skill.json`, `modal.en.skill.json`; `?lang=en` for the English variant).
- One rule, `isForbidden` in `plan.mjs`, used by the driver (`act`), the runner's plan check, the audit, the lint and the blind-kiosk grader (`forbiddenSteps` in `spikes/blind-kiosks/grade/lib.mjs`, which had its own copy of the word list). `FORBIDDEN_WORDS` and the grader's `DEFAULT_FORBIDDEN` are gone.
- A label (each line of a target's text, without spaces, symbols, prices and counts) is a payment or checkout control when it **is** one (주문, 주문하기, 주문완료, 결제, 결제하기, 카드, 카드결제, 간편결제, 신용카드, 체크카드, 신용체크카드, 쿠폰, 상품권, 구매하기, Order, Order now, Place order, Pay, Pay now, Payment, Checkout, Card, Buy now, …), **starts with** 결제, pay or checkout, or **ends with** 주문하기, 결제하기, 구매하기, 주문완료, 결제, checkout, order now, place order, pay now or payment.
- A label with a keep-ordering word (계속, 더 담기, 취소, 이전, continue, back, cancel) is never one for an order word, so `계속 주문하기` and "Continue ordering" can be tapped. It still is when it also names payment (결제, 카드, pay, card, checkout): "Continue to payment", "Back to checkout". This is stricter than "never forbidden" on purpose: a continue-to-payment button must stay out of reach.
- The skill's `forbiddenLabels` now match whole labels, not substrings: listing `주문하기` no longer takes `계속 주문하기` with it.
- Wider than before in places: "Order now", "Place order", "Payment" and "주문하기 12,500원" are refused without a `forbiddenLabels` entry (the old list missed the first three; the fourth was caught by substring).
- Not changed: the prompt, the tools, the gate, pruning and everything else about how the learner explores.
- Tests (failed before, pass after): in `patterns.test.mjs` "I-193: a keep-ordering button is not a payment control; checkout and payment labels still are", "I-193: the driver taps 계속 주문하기 and Continue ordering on a timeout modal, and still refuses 주문하기 and Order now", "I-193: the runner replays an order through the timeout modal, and still refuses a plan with Order now", "I-193: the audit counts Order now as a checkout control without forbiddenLabels, and the lint accepts 계속 주문하기"; in `spikes/blind-kiosks/grade/test/classify.test.mjs` "I-193: forbiddenSteps uses the learner's label rule, so a timeout modal's keep-ordering button is not unsafe". Counts now: patterns 21, learner 12, grader 25, `test_audit.mjs` 4/4; the dev-set Doughhouse holdout with the `results/dev/gemini-doughhouse-after` skill still 4/4 + violation detected (no new learner run on the dev set).

## 10-14, round 3 — interrupts, verified totals, option-group coverage (`29aa175`, then the frozen learner, see `spikes/blind-kiosks/ROUND3.md`)
Informed by test kiosks: the open learner problems I-194 (bk2), I-195 (bk5) and I-197 (bk6, and the skill-total count) were all seen on `spikes/blind-kiosks/` test kiosks, so every rerun of those kiosks with this learner is labelled **informed** and never counts as an unseen-kiosk result (`spikes/blind-kiosks/ROUND3.md`). Built and tested on synthetic fixtures (`fixtures/patterns/interrupt.html`, `review.html`) and the dev set only; the test kiosks' apps, briefs and answer keys were not opened. No kiosk-specific rule or label list was added: the only words are the order-button exception below.

**Skill format** (all new fields optional; older skills replay unchanged, checked with the run-3 Doughhouse skill: holdout 4/4 + violation detected):
- `interrupts: [{ "text", "dismiss": step }]`: popups that can come up between any two steps. Before every step the runner answers each one whose text is visible, with its `dismiss` step under the usual payment rule; when a step fails (a click that timed out under a popup, a target it hid) it answers them again and retries that step **once**. A refused step is never retried. Results list `interruptsAnswered: [{ text, afterError }]` (I-194).
- `review: { "open": [steps], "totalPattern", "close"?: [steps] }` and `charges: [{ "name", "amount", "dineOption"? }]` (I-195). After the order lines the runner reads the cart total as before, then, when the skill has `review`, opens the kiosk's order review and reads the total there. The kiosk's total wins: results carry `kioskTotal`, `skillTotal` (lines plus charges), `totalSource` (`review` or `cart`), `cartTotal`, `reviewTotal`, and a `totalMismatch` text when they differ, which fails the order. `shownTotal`/`expectedTotal` stay (= kiosk and skill total) for older callers.
- **The one exception to the payment rule** (`isReviewOpener` in `plan.mjs`): the step op `openReview` may tap the kiosk's order button to open the review. Only that op, only in `review.open` and at most once, only on a label that is exactly 주문, 주문하기 or Order (a price or count may follow), never a label that also names payment or sending (결제, 카드, pay, card, checkout, 쿠폰, 상품권, 완료, 전송, 접수, 확정, submit, send, place, confirm, complete, now), never a label in the skill's own `forbiddenLabels`. Everything else on the review stays refused (결제하기, 카드 결제, Checkout, Place order, Order now). After `review.open` a **payment control that was not on screen before** must be visible (`isPaymentControl`); if none appears the button may have sent the order (a pay-later device), so the replay stops with `reviewUnsafe: true` and fails. Checked before any click (`unsafeTargets`): order steps, interrupt answers and review close steps under `isForbidden`, `openReview` anywhere else refused.
- When a skill has no `review` and a review opener is visible after the lines, the result says `reviewOpener: "<label>"`.

**Gate** (`learner.mjs`, for the exact same skill as before): besides ≥ 3 different passing orders, none failing, and no lint errors, finish now needs (I-197) every option group of every orderable item to be used by a passing order (`uncoveredGroups` in `plan.mjs`; groups with the same name, options and deltas count once; a group with priced options needs a priced pick, since a 0원 pick cannot show a wrong price; sold-out items are skipped), and `review` when a test order saw the kiosk's order button. An order passes only when the skill's total equals the kiosk's (the review's when declared), as before but now on the review. `testSkill` lists what is missing; its stdout line adds `uncovered=<n>` and `review=<label>`.

**Lint**: interrupts need a text of ≥ 4 letters and a dismiss step that is not a payment control and not an item, category or option name; `review.open` needs at most one `openReview`, on the order button, and no payment control; `review.totalPattern` must be a regex with a group; `openReview` is refused in recipes, `select`, `after`, interrupts and `review.close`; charges need a name, a non-zero whole amount and a `dineOption` from `dineOptions`. Recipes' option-group `select`/`after` steps are now checked for payment controls too.

**Prompt**: describes `interrupts`, the order review and `openReview`, `charges`, and the coverage rule; `forbiddenLabels` now means payment buttons (the order button must not be listed there to be used in `review`); "if you cannot make an option's price match, remove that option (orders with it are then refused) and say why in notes".

**Other**: the audit's replays answer interrupts; `learn-stats.json` records `learner: { commit, dirty }` (I-202). The blind-kiosk grader replays interrupts like the runner and, for a skill with `review`, replays each order a second time with `runOrder` and takes the kiosk total from the review; the menu-cart outcome of grader v2 is kept per order (`cartOnlyOutcome`) and in the summary (`orders.cartOnly`) (`spikes/blind-kiosks/grade/README.md`).

**Second commit, after the dev-set Gureum run** (`results/dev/gemini-gureum-round3/`: 2M token cap at turn 95, not finished). Every `audit` and `testSkill` call sent the whole skill again (about 13k output tokens for 40 items), and those copies stay in the context, because pruning shortens tool responses, never the model's own calls: input per turn grew from 16k at turn 82 to 140k at turn 90, and the coverage gate needs more test calls. Now `testSkill`, `audit` and `finish` reuse the last skill sent when `skillJson` is left out (the prompt says to send it only when it changed); the gate is unchanged, a reused skill is the same exact skill. For the run's own files only: each failed self-test order's error or total mismatch is printed to `learn.log` (`    order <n>: …`), and a run that does not finish writes the last skill it sent to `last-skill.json` (never graded). Tests: `learner.test.mjs` "token budget: testSkill, audit and finish reuse the last skill sent…" and "diagnostics: …" (failed before).

**Tests** (no AI, need Chrome; all failed or did not exist before): `patterns.test.mjs` 33 (12 new: the I-194 modal with and without interrupts, the after-timeout retry, unsafe or vague interrupts; `isReviewOpener`; `openReview` in the driver; the review total with and without charges; `reviewOpener`; a pay-later order button flagged `reviewUnsafe`; a review that taps payment refused before any click; `uncoveredGroups`), `learner.test.mjs` 18 (6 new: skill reuse, failure diagnostics, coverage refusal and acceptance, review-total mismatch refusal, missing review refusal, the commit stamp; the two pattern-4 tests now use a stepper skill with a review and cover the ice group), grader 30 (3 new in `test/round3.test.mjs`), `test_audit.mjs` 4/4.

## 10-14, round 4 — customer choices are option groups, popups that change the order, skill patches (see `spikes/blind-kiosks/ROUND4.md`)
Informed by test kiosks: round 3's fresh `bk7-bubbletea` (0 correct / 10 safe refusals: no sweetness group, `clickIfVisible 50%` in the recipe, the set popup always declined) and `bk8-tableorder` (no skill: 2M cap at turn 99 after a gate that could not be met), and `bk5-restarea`'s I-196. All three are **informed** for round 4 and never count as unseen-kiosk results again. Built and tested on synthetic fixtures (`fixtures/patterns/choice.html`, `choice.skill.json`; `review.html?send=1`) and the dev set; no kiosk-specific label list was added.

**Root cause: the option-name lint** (`lint.mjs`, now `isControlLabel` in `plan.mjs`). An option name had to contain a letter, so `0%`…`100%` were "controls": bk7's test #1 had `lint=100` (5 options × 20 drinks) and the learner dropped the group and tapped `50%` in its recipe ("conflict with the lint rules", its notes). The stepper rule `/(더하기|빼기|증가|감소)$/` matched inside a word, so `곱빼기` (a large portion) was a control: bk5's `lint=5` led to the option `곱배기` (I-196), bk5's round-3 rerun left it out ("린트 키워드 제약으로 인해 제외함"), bk8's `lint=3` led to `곱배기` again. Now a label is a control only when it has no letter **and no digit** (`+`, `−`, `›`), is a navigation word, or ends with a navigation or stepper word **as a whole word** (`수량 빼기`, `콜라 더하기`, `4,000원 담기`, `장바구니 담기`). Numbers and one-word choices are names.

**Skill format** (all new fields optional; every older skill plans the same steps: 28 learned skills checked, none uses the two changed planner cases; the run-3 and round-3 Doughhouse skills replay the holdout 4/4 with the rule violation detected):
- `chooseOptions` may name `"groups"`: it runs only those, where it stands (a set popup after the add button); a `chooseOptions` without `groups` runs the groups no other `chooseOptions` of the recipe names, so one `chooseOptions` still runs them all.
- A conditional group (`appliesWhen`) with no pick whose condition the line did not choose is skipped with its `after` steps (before, its `after` steps ran, e.g. a set's `다음` after "drink only").
- `declines: [{ "choice", "offer" }]`: a popup after adding that changes what is ordered and that the skill always declines by tapping `choice`. The lint wants an `offer`, a `choice` that a recipe step or interrupt taps, and that is not an option, item, category or payment control.
- `sharedGroups: { "<name>": group }` with the name as a string in an item's `optionGroups`, and the tools' `skillPatch`: learner-only ways to write a skill (below); skill.json is always resolved (no `sharedGroups`).

**Lint**: a recipe step (not `startOrder`) or a group's `select`/`after` step written with a fixed label that is an option name of the catalog is refused ("taps … on every order"); a `chooseOptions` `groups` entry must name a group of some item; `declines` as above.

**Audit** (`audit.mjs`; `ok` now also needs no `hardClicks` and no `requiredChoices`):
- Item screens: choices are now also plain look-alike buttons in a row (same tag, role and first class under a near ancestor; `newTappables` in `driver.mjs`), not only radios, checkboxes and "+n원" labels; controls, payment buttons, yes/no answers and disabled (sold-out) buttons are not choices. `missingOptions` stays informational (finish refuses once).
- Line probes: for each kind of orderable item (category, recipe, group shapes, left-out choices) the simplest line (first option of each required group that applies, quantity 1) is replayed on a fresh kiosk with an inspection hook in `act` (`opts.inspect`). A step written with a fixed label after the item is opened (or an interrupt answer) that taps one of several look-alikes (`lookAlikes` in `driver.mjs`) is a **hard click**: always on the item's own screen; on a popup after it only when the popup shows prices and the skill does not declare the tap in `declines`. An item whose screen shows choices the skill leaves out, and whose simplest line the kiosk does not add (cart total ≠ the line's price, or a step fails), is listed in **`requiredChoices`**. Other failed lines are listed in `failedLines` (informational).
- A tappable counts as a priced tile only when an amount on it is **not zero**: a running total ("🧾 주문 내역 0원") is a control. On bk8 that button kept every round-3 audit at `missing=1`, so finish could never be accepted.
- Speed: item screens and line probes are kept for the rest of the process (`resetAuditMemo` for tests): a second audit of the same skill opens nothing; a changed recipe replays lines but reuses item screens. Measured on the dev set: Gureum (`fixtures/a_v3.json`) first audit 68 s, the next 4 s (each audit took about 25 s before); Doughhouse 13 s then 2 s. `test_audit.mjs` as a whole takes about 3 min (was 1.5 min) because each case is a first audit.

**Learner** (`learner.mjs`, `skill.mjs`):
- `testSkill`, `audit` and `finish` take **`skillPatch`**: a JSON merge patch on the last skill (objects merge, `null` deletes, lists replace; `catalog` entries merge by `name`, `{"name","remove":true}` drops one). On bk7 7 of 76 turns resent the whole ~13k-token skill (about 78k of 83k output tokens, ~1 min of generation each), and every copy stayed in the context.
- **`sharedGroups`**: a group several items share is written once and listed by name.
- **Pay-later devices**: once a self-test reports `reviewUnsafe` (no payment step after the order button), the gate stops asking for `review` for that button, and `testSkill` says to drop `review`. On bk8 test #4 passed 3 of 3 but the gate wanted `review`, and with `review` every order failed as `reviewUnsafe`: the gate could not be met.
- Prompt: choices with no price, with a default or required without one are option groups; never tap a choice in a recipe; numbers are names; a popup after adding that changes the order is modelled with a second `chooseOptions` `groups` (or declared in `declines` when its offer was not seen); `skillPatch`, `sharedGroups`; leave `review` out when testSkill says the order button sends orders.
- The audit line in `learn.log` adds `hardClicks`, `requiredChoices` and how many item screens and lines it opened.

**Grader** (`spikes/blind-kiosks/grade/lib.mjs`, pre-registered in ROUND4.md before any round-4 fresh run): a key option whose label is a skill's declared `declines` choice is left out of the line, like a kiosk default; the offer itself stays refused.

**Tests** (no AI, need Chrome; each failed or could not load before its code): `patterns.test.mjs` 44 (11 new: digits and symbols in option names; 곱빼기 vs 수량 빼기; a recipe tapping an option name; `chooseOptions` `groups` and the skipped conditional group; the set replay; the audit on the modelled skill, a tapped item-screen choice, a left-out required choice, a declined popup with and without `declines`; the audit memo; the 0원 running total), `learner.test.mjs` 21 (3 new: `skillPatch`, `sharedGroups`, the pay-later gate), `viewport.test.mjs` 1, grader 33 (1 new: `declines`), `test_audit.mjs` 4/4.
