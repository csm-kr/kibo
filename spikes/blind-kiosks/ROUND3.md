# KIBO Learn, round 3 (10-14)

Round 3 fixes three open learner problems found on the blind kiosks: a popup that comes up in the middle of a line (I-194, bk2), a phone total that can differ from what the kiosk charges (I-195, bk5), and skills whose own total was wrong because self-tests never used some option groups (I-197, bk6, and 7 of 48 phase 13 orders). The fixes are general (no kiosk-specific rule, no label list tuned to a kiosk), built test-first on synthetic fixtures and the dev set.

**Every test-kiosk number in this file is "informed".** The learner changed after its developer saw the failures of bk2, bk5 and bk6, so their reruns here never count as unseen-kiosk results. The reported phase 13 numbers (`RESULTS.md`) stay as they are; round 3 is reported beside them, never instead of them.

**Frozen learner: commit `ea28477`** (`spikes/kibo-learn/` and `spikes/blind-kiosks/grade/`). Every test-kiosk run below started from it with a clean tree (`learn-stats.json` → `learner: { commit, dirty: false }`). Later commits change no file in those two folders (check: `git diff --stat ea28477 HEAD -- spikes/kibo-learn spikes/blind-kiosks/grade` is empty).

## What changed and why
Details and test names: `spikes/kibo-learn/CHANGES.md` "round 3". All new skill fields are optional: older skills replay unchanged (the run-3 Doughhouse skill `spikes/kibo-learn/results/run3/skill.json` still replays its holdout 4/4 with the rule violation detected).

1. **Interrupts (I-194).** A skill may list `interrupts: [{ "text", "dismiss" }]`: a popup's identifying text and the one step that closes it while keeping the order. Before every step the runner answers each listed popup whose text is visible; when a step fails (a click that timed out under the popup, a target it hid) it answers them again and retries that step once. A refused step is never retried. The dismiss step obeys the payment rule like any step, and the lint refuses a dismiss that is a payment control or an item, category or option name, and a text shorter than 4 letters. Why: on bk2 the timeout modal came up between two steps of a line, where a recipe could not answer it.
2. **Verified totals (I-195).** A skill may declare `review: { "open", "totalPattern", "close"? }`, the steps that open the kiosk's own order review and the pattern for the total it shows there, and `charges` (per-order amounts, optionally for one dine choice). After the lines the runner reads the cart total as before, then opens the review and reads the kiosk's total there. **The kiosk's total wins**: results carry `kioskTotal`, `skillTotal`, `totalSource`, `cartTotal`, `reviewTotal`, and a `totalMismatch` flag that fails the order when the two differ. Why: the phone must quote what the kiosk will charge, and charges can appear only on the review.
3. **One narrow exception to the payment rule.** Opening the review needs one tap on the kiosk's order button, which the rule refuses. The op `openReview` may tap it, and only it: only in `review.open` and at most once; only a label that is exactly 주문, 주문하기 or Order (a price or count may follow); never a label that also names payment or sending (결제, 카드, pay, card, checkout, 쿠폰, 상품권, 완료, 전송, 접수, 확정, submit, send, place, confirm, complete, now); never a label in the skill's own `forbiddenLabels`. After it, **a payment control that was not on screen before must appear**; if none does, the button may have sent the order (a pay-later device), so the replay stops with `reviewUnsafe` and fails. Everything else stays refused, on the review too (결제하기, 카드 결제, Checkout, Place order, Order now; tested). I-193 showed what a broad word list does, so the exception is one op, three labels and a check after the tap.
4. **Coverage (I-197).** The finish gate now also needs every option group of every orderable item to be used by a passing self-test, and an order passes only when the skill's total equals the kiosk's (on the review when declared). Groups with the same name, options and deltas count once; a group with priced options counts only for a priced pick (a 0원 pick cannot show a wrong price). It also needs `review` when a test order saw the kiosk's order button. `testSkill` lists what is missing.
5. **Skill reuse (dev-set finding).** On the first Gureum dev run every `audit` and `testSkill` re-sent the whole ~13k-token skill, and those copies stay in the context (pruning shortens tool responses, never the model's own calls), so input per turn grew from 16k to 140k within 8 turns. `testSkill`, `audit` and `finish` now reuse the last skill sent when `skillJson` is left out.
6. **Records.** `learn-stats.json` names the learner commit and whether `spikes/kibo-learn/` had uncommitted changes (I-202); `learn.log` explains each failed self-test order; an unfinished run writes `last-skill.json`.
7. **Grader** (rules unchanged, `GRADER_VERSION` 2): it replays interrupts like the runner, and for a skill with `review` it replays each order a second time with the runner and takes the kiosk total from the review. The plain grader-v2 outcome from the menu cart's total is kept per order (`cartOnlyOutcome`) and in the summary (`orders.cartOnly`) (`grade/README.md`).

### What worked, what did not
- **I-194, fixed on bk2.** The learner declared the timeout modal as an interrupt; the runner answered it in h1, h5, h8, h9 and h10, the five orders that were unsafe in phase 13, and all 10 orders are correct. The menu cart total and the review total agree in all 10.
- **I-195, the verified-total machinery works, but the bk5 hypothesis was wrong.** bk2, bk5 and bk6 all declared their order review; every `openReview` step, while exploring and in the skills, named `주문하기` (traces and `skill.json`), and no tap was refused as a payment control in any run (traces). On bk6 the kiosk totals came from the review in 10 of 10. On bk5 the review shows the same total as the cart (11,500 for h3). An AI-free replay of h3 printed the review: `… 봉투가 필요하신가요? 봉투 +100원 … 총 결제금액 11,500원`. The 100원 is an optional **bag** on the review, and the answer key's three take-out orders ask for it as an order-level option (`orderOptions.bag`, read after this run; the learner was already frozen). The grader ignores `orderOptions`, so it replays those orders without the bag and calls them unsafe, where its own rules would refuse them safely (new issue in `docs/ISSUE.md`; the grade is not changed, so bk5 stays 4 / 3 / 3, as in phase 13). The skill format cannot express an order-level choice on the review, and the gate never asks for a take-out self-test (new issues).
- **I-197, better, not solved.** bk6's own total was wrong in 4 of 10 orders, now 2 (h2, h3); bk2's in 0 of 10. The remaining two are the per-person ticket discount: the self-tests used the discount with one person, where skill and kiosk agree, and the skill format cannot price "per person". A phone would quote the runner's verified kiosk total and see the flag.
- **The stricter gate costs finishing on a big kiosk.** On Gureum Darak Coffee (dev set, about 22 distinct option groups) the round-3 learner did not finish in either run (2M cap at turns 95 and 111). The second run had the skill-reuse change; it still spent most of its budget exploring and then met option labels its recipe could not find. The test kiosks have 4–10 groups and all three finished.
- **Not addressed:** the misspelled option name on bk5 (`곱배기`, I-196, 3 refusals again), conditional groups on bk6 (0/4), bk6's `cartTotalPattern` that matches nothing on the menu screen (unchecked when a review is declared; new issue).

## What the product bridge should adopt (proposal, not built)
`src/` was not changed (another session owns it). The product bridge (`src/lib/bridge/`, `src/lib/adapters/learned.ts`) replays skills in a different format, so each point needs the skill converter too.
1. **The whole-label payment rule first.** `isForbiddenLabel` in `src/lib/adapters/learned.ts` still matches substrings (`label.includes(f)`). With a skill whose `checkout.label` is 주문하기, it refuses `계속 주문하기`, so the bridge could never answer bk2's modal. Port `isForbidden` from `spikes/kibo-learn/plan.mjs` (with its tests in `patterns.test.mjs` "I-193 …").
2. **Interrupts.** `skillSchema`: `interrupts: z.array(z.strictObject({ text: text.min(4), dismiss: recipeStep })).max(5).optional()`, refined so `dismiss` targets a label that is neither forbidden nor an item, category or option label; carry it on `LearnedKiosk`. `runPlan(doc, plan, { forbiddenLabels, interrupts })`: before each step, for each interrupt whose text is in `doc.body.innerText` and whose dismiss target `locate`s to exactly one element that passes `isForbiddenTarget`, click it and `settle`; when `locate` throws (no click has happened yet), answer interrupts and retry that one step once. A step whose click happened is never retried, which keeps the bridge's "nothing is retried (double-add risk)" promise. The bridge clicks with `el.click()`, which a covering modal does not block, so there the risk is the modal's countdown emptying the cart; the before-step check covers it.
3. **Charges.** `charges: [{ name, label, amount, dineOption? }]` in the skill, added once per order to the session total the phone quotes on a learned kiosk.
4. **Verified total at checkout (needs the user's decision).** Today the bridge never taps `checkout.label` (the skill schema comment and `docs/SECURITY.md` "Learned kiosks"). The proposal: at `requestCheckout` on a learned kiosk, the bridge runs `review.open`, whose single `openReview` step must name `checkout.label` and pass the whole-label opener rule; it then requires a payment control that was not on screen before, reads `review.totalPattern`, and adds `reviewTotal` to `bridgeReport`. The confirm card shows the kiosk's total, flags a difference from the session total, and the user pays on the kiosk by touch as now; the bridge taps nothing else. If no payment control appears, it reports `ok: false` and calls staff. This changes a security rule, so it needs an ADR and the user's consent (`docs/ISSUE.md`).

### Rules fixed before the fresh runs (orchestrator, 10-14 ~12:00 KST)
Written and committed before either fresh kiosk was learned. The orchestrator read the two answer keys' order-level field names (not the apps' code) and rendered bk8's start screen once at the learner's default size, to write these rules; nobody changed learning logic after that.
- **Kiosks:** `bk7-bubbletea` (bubble tea shop, portrait kiosk) and `bk8-tableorder` (table-order tablet at a Korean BBQ restaurant, landscape 1280×800, orders are sent to the kitchen and paid at the counter). - **Device size:** bk8's page is a fixed 1280×800 landscape screen; at the learner's default 1080×1600 its right edge is off screen. The browser gets the device's size through `KIOSK_VIEWPORT=1280x800` (new in `driver.mjs`, default unchanged, `viewport.test.mjs`) for learning and grading bk8. bk7 uses the default like every earlier kiosk. This is a screen setting taken from the brief, not a learning rule; learning logic stays as frozen in `ea28477`.
- **Dine choice:** these keys name it `orderType` (`eatIn`/`takeOut`); the grader reads it like `dine` (`resolveDine`, test in `translate.test.mjs`). bk5's `mode` field is read the same way; bk5's numbers above are not re-graded.
- **Pay-later device (bk8):** KIBO stops before the control that sends an order to the kitchen, as it stops before payment. An order is graded on its own amount, `orderTotal`, when the key gives one (`gradedTotal`); `expectedTotal` there is the running table total.
- **Follow-up orders (`startsAfter`, bk8 h7 and h10):** they assume an earlier order was already sent to the kitchen, which KIBO never does. They are replayed as written on a fresh table and graded on `orderTotal`, but reported in their own row and left out of the headline count (8 orders). bk8 h7 asks for 1 portion of meat, which the kiosk allows only after a meat order was sent, so a refusal there is expected.
- **Staff calls (bk8 h5):** not order lines; the order total excludes them, as the key does.
- **Everything else:** grader v2 with round 3's review totals and interrupts, at this commit; one learning run per kiosk (`gemini-3.8-flash`, 2M input-token cap, 30 min kill, `TRACE_DIR`), no rerun except once after a crash; both reported whatever the result.
